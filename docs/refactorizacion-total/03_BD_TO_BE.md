# Base de datos TO-BE y ERD completo

**83 tablas propuestas: 68 de aplicación (incluyen users y migration_links) y 15 conservadas de Laravel/Spatie.** 14 módulos propietarios. El número deriva de separar conceptos e historiales necesarios, no de reducir o aumentar tablas artificialmente. PostgreSQL; Laravel + Blade + Livewire.

## Convenciones físicas obligatorias

- Tablas de aplicación: id bigint GENERATED BY DEFAULT AS IDENTITY, PK; código visible separado cuando corresponde. No MAX+1. Cada tabla incluye created_at/updated_at timestamptz, recorded_by/updated_by bigint nullable FK users, lock_version integer default 0. Usuario puede ser nulo solo para legado/importación o sistema identificado por procedencia; escrituras humanas nuevas exigen actor.
- Todas incluyen legacy_code text nullable para búsqueda de origen; la correspondencia uno-a-muchos completa reside en migration_links. No imponer unicidad global de códigos heredados. A las tablas de aplicación se añade archived_at/archived_by/archived_reason; FK archived_by→users.
- Perfiles H y V incluyen status text (si ya declarado, no duplicar), supersedes_id nullable FK a la MISMA tabla, voided_at, voided_by FK users y void_reason. Solo una sucesora válida por versión mediante índice único parcial; impedir ciclos y cambios de sujeto con Action. Los hechos firmados no se sobreescriben. Anulación es metadata auditada, no DELETE.
- Perfiles W/T incluyen historial de transiciones en activity_log (estado anterior/nuevo, motivo, actor, request ID). Cuando cambia contenido clínico firmado se crea versión H/V; activity_log no guarda el contenido clínico como único respaldo.
- Tipo ? indica nullable. FK sin ? obligatoria. U(...) es restricción UNIQUE. Todos los *_id declarados con flecha son FK reales salvo referencias polimórficas técnicas explícitas. ON DELETE RESTRICT para dominio histórico, autor y evidencia; no cascadas clínicas. Se conservan cuentas deshabilitadas como autor.
- Fechas civiles date, horas recurrentes time; eventos timestamptz UTC con zona institucional America/La_Paz configurable. Unir fecha/hora legada requiere marcar precisión y zona en procedencia. Intervalos [inicio,fin), fin abierto no significa fecha inventada.
- Dinámicos clínicos: JSONB solo para respuestas/formularios versionados, reglas y snapshots con esquema validado. No EAV universal, ni JSON para sustituir FKs operativas. Los campos numéricos de signos y dosis usan numeric, nunca float monetario ni cadenas para calcular.
- Índices mínimos: cada FK consultada; series (person_id,momento DESC), bandejas (status,momento), U(public_code), U(lower(users.email)), claves de idempotencia. Paginación obligatoria.
- Un dato clínico con admission_id debe pertenecer a su persona; caso/estancia simultáneos solo si admission.admission_case_id coincide. Imponer con trigger de integridad o FK compuesta donde viable, además de Action. CareTaskExecution/vital/administración también deben compartir persona por su cadena de padres.
- Sin extensiones nuevas: exclusión temporal mediante transacción con bloqueo FOR UPDATE de cama/estancia/persona y comprobación de solape; trigger PostgreSQL aplica la misma regla a escrituras fuera de Laravel. Índices únicos parciales refuerzan una asignación abierta. Una EXCLUDE GiST con btree_gist es alternativa futura sujeta a aprobación, no requisito de este diseño.

En nodos técnicos framework_key es una etiqueta del diagrama, **no columna nueva**; sus PK reales se detallan abajo. Cardinalidades máximas uno-a-uno (persons/users, persons/residents, persons/professionals, persons/volunteer_profiles, caso/estancia) se restringen por las U del diccionario; el dibujo genérico de FK muestra dependencia y la U reduce el máximo a uno.

## Invariantes de negocio y cobertura

1. Persona existe antes de residente. Prevaloración se vincula a person + admission_case; rechazar no elimina historia clínica. No se obliga a crear User para familiar/voluntario/profesional.
2. Estancia única por caso: aprobación repetida devuelve la ya creada con request_key; reingreso abre caso/estancia nuevos del mismo residente. Alta y transferencia bloquean estancia/camas y cierran intervalos; no infieren alta por archivar expediente.
3. Profesional es persona acreditada; cargo pertenece a vínculo laboral; especialidad depende de profesión; rol solo concede capacidades. Cambiar rol no altera datos laborales.
4. Prescripción nueva/modificada requiere competencia, firma y pauta completa; administración valida persona, línea vigente, momento y omisión. Corregir una administración enlaza misma administration_group; jamás dispara otra dosis. Además de U(request_key), imponer índice único (prescription_item_id, scheduled_at) WHERE supersedes_id IS NULL AND scheduled_at IS NOT NULL para hechos raíz de dosis programadas: dos request keys distintos tampoco permiten duplicar la misma dosis. Una corrección conserva grupo, línea y momento programado; PRN sin hora programada usa grupo propio y validación de intervalo/dosis acumulada según pauta aprobada.
5. care_plan_versions congela instrucciones; tareas futuras usan versión vigente, ejecutadas conservan la anterior. Dieta y rehabilitación son tipos de plan/atención, no tablas por profesión.
6. Documento cambia por nueva versión; consentimiento y receta referencian versión exacta. Regenerar un PDF no cambia la evidencia firmada. Descargar requiere política del titular, no solo conocer URL.
7. Los históricos originales ambiguos se preservan cifrados en migration_links, fuera de toda operación clínica normal. Incidencia no resuelta se excluye de automatismos y se muestra como dato pendiente; nunca inventar fechas, consentimiento, firma, dosis o acreditación.
8. No tablas de pagos: la única evidencia actual es una ruta de dashboard estado-cuenta sin modelo/operación. Desactivar ese enlace hasta aprobar un alcance de facturación separado (D12). Esto no elimina una función operativa existente.
